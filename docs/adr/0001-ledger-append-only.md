# 0001. 크레딧 원장은 추가만 하고, 잔액은 원장에서 파생된 캐시로 둔다

- 상태: 채택 (PLANDIT-3)
- 관련 코드: `apps/api/src/credit/ledger.service.ts`, 마이그레이션 `20260928074931_credit_ledger`

## 맥락

크레딧은 돈이다. 충전(결제 승인), 차감(문자 발송), 환불(발송 실패), 운영자 조정이 서로 다른 경로(웹 요청, 웹훅, 워커, 재조회 작업)에서 동시에 일어난다.
잔액 한 칸만 두고 `UPDATE balance = ?`로 바꾸면 세 가지를 답할 수 없다.

- 지금 잔액이 왜 이 값인가? (고객 문의, 정산)
- 같은 요청이 두 번 들어왔을 때 두 번 반영됐는가?
- 잔액이 어긋났다면 어디서부터 틀렸는가?

## 결정

1. **모든 변동은 `credit_ledger` 행 하나다.** 종류(CHARGE·DEBIT·REFUND·ADJUST), 금액(부호 포함), 근거(`refType`, `refId`), 그리고 **그 시점 잔액 `balance_after`**를 함께 남긴다.
2. **원장은 추가만 한다.** DB 트리거가 `UPDATE`와 `DELETE`를 막는다. 잘못된 반영은 지우지 않고 반대 방향 행(REFUND, ADJUST)으로 바로잡는다.
3. **`credit_accounts.balance`는 캐시다.** 원장 합계와 같아야 하고, 어긋나면 `LedgerService.recalculate()`로 원장에서 다시 계산한다. 애플리케이션 코드가 잔액을 직접 쓰는 곳은 없다.
4. **변동은 `LedgerService.append()` 한 곳으로만.** 한 트랜잭션 안에서 다음 순서를 지킨다.
   1. 계정 행을 `SELECT … FOR UPDATE`로 잠근다.
   2. 멱등키를 다시 확인한다. 같은 키로 이미 기록됐으면 그 행을 돌려주고 아무것도 바꾸지 않는다.
   3. `UPDATE … SET balance = balance + amount WHERE balance + amount >= 0 RETURNING balance`로 잔액 계산을 **SQL 안에서** 한다. 조건에 걸리면 잔액 부족(`INSUFFICIENT_CREDITS`)이다.
   4. 원장 행을 넣고 `balance_after`에 방금 받은 값을 쓴다.
5. **모든 변동은 멱등키를 받는다.** 예를 들어 `PAYMENT:{id}:CHARGE`, `REMINDER_DELIVERY:{id}:DEBIT`, `REMINDER_DELIVERY:{id}:REFUND`처럼 "무엇 때문에 생긴 변동인가"로 키를 만든다. 같은 키에 다른 금액이 오면 `IDEMPOTENCY_CONFLICT`로 거절한다.
6. `append(input, tx?)`는 호출자의 트랜잭션에 합류할 수 있다. 웹훅 이벤트 저장과 원장 반영이 한 커밋이 되게 하려는 것이다([0003](0003-webhook-idempotency.md)).

## 버린 대안

- **잔액 한 칸만 갱신**: 가장 단순하지만 이력·중복 여부·복구 근거가 없다.
- **애플리케이션에서 `잔액 - 금액`을 계산해 저장**: 두 요청이 같은 잔액을 읽고 각자 빼면 한쪽 차감이 사라진다(잃어버린 갱신). 잠금이 있어도 계산을 SQL에 두는 편이 실수할 여지가 적다.
- **원장만 두고 잔액은 매번 합계로 계산**: 정확하지만 조회가 원장 크기에 비례해 느려진다. 캐시 + 재계산 도구로 절충했다.

## 결과

- 잔액이 어떤 행들의 합인지 언제나 설명할 수 있고, 캐시가 틀려도 원장으로 복구된다.
- 같은 요청이 몇 번 와도 잔액은 한 번만 바뀐다.
- 대가: 모든 변동이 계정 행 잠금을 거치므로 한 워크스페이스 안의 변동은 줄을 선다. 워크스페이스 단위라 현재 규모에서는 문제가 되지 않는다.
- 트리거는 `TRUNCATE`는 막지 않는다. 테스트 DB 초기화용이며, 운영 DB에서 쓰지 않는다.

`apps/api/test/credits.e2e-spec.ts`

- 충전·차감이 `balanceAfter`를 남기고 캐시와 맞는다.
- 잔액보다 큰 차감은 거절되고 아무것도 기록되지 않는다.
- 같은 멱등키 재호출은 부작용이 없고, 다른 내용으로 키를 재사용하면 거절된다.
- DB가 원장의 `UPDATE`·`DELETE`를 거부한다.
- 잔액 30에 1크레딧 차감 50개를 동시에 보내면 **정확히 30개만** 성공하고, `balanceAfter`는 29 → 0으로 하나씩 줄어든다.
- 어긋난 캐시를 원장 합계로 되살린다.
