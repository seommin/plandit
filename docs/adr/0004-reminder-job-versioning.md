# 0004. 리마인더 예약 작업은 발송 시각을 id에 담고, 옛 작업은 실행할 때 스스로 버린다

- 상태: 채택 (PLANDIT-7)
- 관련 코드: `apps/api/src/reminder/reminder.queue.ts`, `apps/api/src/reminder/reminder-dispatch.service.ts`, `apps/api/src/reminder/reminder-time.ts`

## 맥락

리마인더는 "일정 시작 N분 전"에 나가야 한다. BullMQ의 지연 작업으로 예약하는데, 일정은 예약 뒤에도 바뀐다.

- 시간이 옮겨지면(끌어서 이동, 편집) 옛 시각의 작업은 나가면 안 되고, 새 시각에 나가야 한다.
- 일정이 지워지거나 알림이 빠질 수 있다.
- 워커는 여러 대일 수 있고, 같은 작업이 재시도될 수 있다.

예약된 작업을 찾아서 지우는 방식은 경합에 약하다. 지우는 순간 이미 워커가 집어 갔을 수 있고, 지우기에 실패하면 옛 시각에 문자가 나간다. 유료 문자는 크레딧이 빠지므로 틀리면 돈 문제가 된다.

## 결정

1. **작업 id에 발송 시각을 넣는다:** `fire_{reminderId}_{fireAt epoch}`. 같은 알림, 같은 시각이면 같은 id라 BullMQ가 중복 예약하지 않는다. 시각이 바뀌면 **새 id의 새 작업**이 생긴다(BullMQ 사용자 지정 id에는 `:`를 쓸 수 없어 `_`를 쓴다).
2. **옛 작업은 지우지 않는다. 실행될 때 스스로 확인한다.** 워커는 작업에 담긴 시각과 **지금 DB 기준으로 다시 계산한 발송 시각**을 비교한다. 다르면(일정이 옮겨짐) 또는 일정이 취소·삭제됐으면 `stale`로 아무것도 하지 않는다.
3. **일정을 수정하면 `syncEvent()`가 모든 알림을 다시 예약한다.** 시각이 그대로인 알림은 같은 id라 그대로이고, 바뀐 알림만 새 작업이 생긴다. 이미 지난 시각은 예약하지 않는다(늦은 알림은 보내지 않는다).
4. **발송 시각 계산은 한 함수(`fireAtFor`)로만 한다.** 시간 일정은 시작 − N분이다. 종일 일정은 캘린더 시간대의 **당일 09:00** − N분이다(서머타임 반영). 예약할 때와 실행할 때가 같은 함수를 써야 2번의 비교가 성립한다.
5. **실행 뒤 단계도 멱등하다.**
   - 받는 사람별 발송 건은 `unique(reminderId, userId, fireAt)`이라 작업이 재시도돼도 한 건이다.
   - 건별 발송 작업 id는 `send_{deliveryId}`다.
   - 중계사에는 `clientRef = deliveryId`로 보내 같은 문자가 두 번 나가지 않는다.
   - 차감·환불은 발송 건 id로 만든 원장 멱등키를 쓴다([0001](0001-ledger-append-only.md)).

## 버린 대안

- **예약 작업을 찾아 지우고 다시 넣기**: 지우기와 실행이 경합한다. 지우기가 실패하면 틀린 시각에 문자가 나간다.
- **작업 id를 알림 id로만**: 시각이 바뀌어도 같은 id라 새 작업이 옛 작업과 충돌한다. BullMQ는 같은 id의 작업을 새로 받지 않는다.
- **분 단위 폴링(매분 "지금 보낼 것" 조회)**: 단순하지만 정확도가 분 단위이고, 규모가 커지면 매분 전체를 훑는다. 지연 작업은 필요한 시각에만 깨어난다.

## 결과

- 일정을 몇 번 옮겨도 마지막 시각에만 한 번 나간다. 옛 작업은 큐에 남았다가 실행 시 무해하게 끝난다.
- 대가: 옛 작업이 실행 시각까지 Redis에 남는다(작은 데이터). 완료·실패 작업은 최근 1,000개만 보관한다.

## 이 결정을 지키는 테스트

- `apps/api/src/reminder/reminder-time.spec.ts`(단위): 시간 일정, 종일 일정(UTC·KST 자정 저장 모두), 서머타임 경계에서의 발송 시각.
- `apps/api/test/reminders.e2e-spec.ts`: 일정을 옮기면 옛 시각에는 0건이 나가고 새 시각의 작업이 존재한다. 실제 BullMQ 워커와 모의 중계사 프로세스로 수신자 100명(30명 실패, 초당 제한으로 429 재시도 발생)을 보내고 `차감 = 성공 차감 + 실패 환불`, 이중 환불 0건을 확인한다.
