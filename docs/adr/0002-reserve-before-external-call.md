# 0002. 외부 서비스를 부르기 전에 우리 쪽 상태를 먼저 기록한다

- 상태: 채택 (PLANDIT-5, 6, 7)
- 관련 코드: `apps/api/src/payment/payment.service.ts`(`charge`), `apps/api/src/payment/payment-reconcile.service.ts`, `apps/api/src/reminder/reminder-dispatch.service.ts`

## 맥락

PG 결제 요청이나 문자 발송 요청은 네트워크를 건넌다. 요청은 도착했는데 응답이 사라지는 경우(타임아웃, 연결 끊김, 우리 프로세스 재시작)가 반드시 생긴다.
이때 우리 DB에 아무 기록이 없으면 "PG에는 결제가 있는데 우리는 모르는" 거래가 생긴다. 고객은 돈을 냈는데 크레딧이 없고, 누가 찾아내기 전까지 아무도 모른다.

## 결정

1. **외부 호출 전에 내부 행을 먼저 저장하고 커밋한다.**
   - 충전: `payments`를 `RESERVE`로 저장한다(거래 번호 `P{yyMMdd}-{seq}`는 DB 시퀀스로 발급). 그다음 PG를 부른다.
   - 리마인더: 받는 사람마다 `reminder_deliveries`를 `QUEUED`로 저장한다. 그다음 중계사를 부른다.
2. **응답을 해석할 수 없으면 `UNKNOWN`으로 둔다.** PG가 명확히 거절(4xx)하면 `FAILED`로 끝낸다. 타임아웃·5xx·연결 실패는 PG에 기록됐을 수도 있으므로 `UNKNOWN`으로 두고 사용자에게 502를 돌려준다.
3. **확정은 재조회 작업이 책임진다.** 워커의 주기 작업이 오래된 `RESERVE`·`UNKNOWN` 결제를 거래 번호로 PG에 다시 물어 확정한다. 응답이 유실돼 PG 거래 id를 몰라도 우리가 만든 거래 번호로 찾을 수 있다.
   - 승인이면 웹훅과 **같은 함수·같은 멱등키**로 반영한다.
   - PG가 모르는 거래면 `FAILED`(`PG_NOT_FOUND`)로 닫는다. 아무도 결제할 수 없으니 안전하다.
   - 아직 결제 전이면 기다리다 24시간 뒤 `EXPIRED`로 닫는다.
   - 문자도 같다. `SENT` 후 결과가 오지 않으면 중계사에 다시 묻고, 중계사에 기록이 없으면 `FAILED`(`RELAY_LOST`)로 닫고 환불한다.
4. **외부 쪽도 멱등하게 부른다.** 결제는 같은 거래 번호로, 문자는 같은 `clientRef`(발송 건 id)로 다시 불러도 한 건만 생기게 한다. 그래서 재시도가 안전하다.
5. 유료 문자는 **발송 전에 차감**하고, 실패가 확정되면 환불한다. 발송 후 차감하면 "보냈는데 못 받은" 상태가 생긴다.

## 버린 대안

- **외부 호출 후 결과만 기록**: 응답 유실 시 흔적이 남지 않는다. 가장 흔한 실수이고 이 결정이 막으려는 것이다.
- **외부 호출을 DB 트랜잭션 안에서**: 느린 외부 응답 동안 행 잠금·커넥션을 붙잡는다. 게다가 외부 호출은 롤백되지 않아서 일관성도 얻지 못한다.
- **분산 트랜잭션(2단계 커밋)**: 외부 PG·중계사가 지원하지 않는다.

## 결과

- 모든 외부 거래에 대응하는 내부 행이 있다. 확정되지 않은 것은 상태(`RESERVE`·`UNKNOWN`·`QUEUED`·`SENT`)로 드러나고, 재조회 작업이 결국 닫는다.
- 운영자가 볼 곳이 분명하다: "N분 넘게 `UNKNOWN`인 결제"가 곧 조사 대상이다(`docs/runbook.md`).
- 대가: 재조회 작업과 만료 규칙이라는 움직이는 부분이 더 생긴다. 그래서 워커는 주기당 작업 하나(BullMQ 작업 스케줄러)로 여러 대가 떠도 중복 실행되지 않게 했다.

## 이 결정을 지키는 테스트

- `apps/api/test/payments.e2e-spec.ts`: PG가 죽어 있으면 502와 함께 `UNKNOWN`으로 남는다.
- `apps/api/test/reconcile.e2e-spec.ts`: 웹훅이 오지 않는 시나리오(`05`) → 재조회로 승인, 원장 1행 → 늦게 온 웹훅은 `ALREADY_APPLIED`로 원장이 늘지 않는다. PG에 닿지 못한 거래는 `FAILED`, 미결제는 25시간 뒤 만료. 실제 BullMQ 워커가 스케줄에 따라 스스로 실행한다.
- `apps/api/test/reminders.e2e-spec.ts`: 결과 웹훅이 사라져도 재조회 작업이 중계사 기록으로 확정한다.
