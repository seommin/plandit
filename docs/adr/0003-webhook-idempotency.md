# 0003. 웹훅은 서명을 확인하고, 이벤트 id와 원장 멱등키로 두 번 걸러낸다

- 상태: 채택 (PLANDIT-5, 7)
- 관련 코드: `apps/api/src/payment/payment-webhook.service.ts`, `apps/api/src/reminder/relay-webhook.service.ts`, `apps/api/src/common/safe-equal.ts`

## 맥락

PG와 문자 중계사는 결과를 웹훅으로 알려준다. 웹훅은 이렇게 온다.

- **두 번 이상** 온다. 우리 응답이 늦거나 유실되면 보낸 쪽이 다시 보낸다.
- **안 올 수도** 있다. 이 경우는 재조회 작업이 맡는다([0002](0002-reserve-before-external-call.md)).
- **늦게, 순서가 바뀌어** 온다. 재조회가 먼저 승인한 뒤에 원래 웹훅이 도착하기도 한다.
- **누구나 보낼 수 있는 주소**다. 인증 없이 받으면 가짜 "승인"으로 크레딧을 만들 수 있다.

## 결정

1. **서명부터 확인한다.** 보낸 쪽이 **원문 본문(raw body)** 에 HMAC-SHA256 서명을 붙인다(`X-Mock-Signature`).
   - JSON을 다시 직렬화하면 바이트가 달라지므로 파싱 전 원문으로 계산한다.
   - 비교는 `timingSafeEqual`로 한다.
   - 틀리면 401을 주고 아무것도 기록하지 않는다.
2. **이벤트 id를 유니크로 저장한다.** `payment_events.event_id`, `relay_events.event_id`에 유니크 제약을 둔다. 같은 이벤트가 다시 오면 삽입이 0건이 되고, `DUPLICATE_EVENT`로 200을 돌려준다.
3. **원장 멱등키로 한 번 더 막는다.** 다른 이벤트 id로 같은 결제의 승인이 또 오는 경우(PG 재발행, 재조회가 먼저 처리한 경우)를 대비한다. 원장 반영은 `PAYMENT:{id}:CHARGE` 같은 키로 하므로 두 번째는 기존 행을 돌려받고 끝난다(`ALREADY_APPLIED`).
4. **이벤트 저장, 상태 전이, 원장 기록은 한 트랜잭션이다.**
   1. 이벤트를 저장한다.
   2. 결제(또는 발송 건) 행을 `FOR UPDATE`로 잠근다.
   3. 금액을 대조한다.
   4. 상태를 전이한다(`RESERVE`·`UNKNOWN` → `APPROVED`·`FAILED`).
   5. 원장을 기록한다.

   중간에 예외가 나면 전부 롤백되어 이벤트도 남지 않는다. 그래서 보낸 쪽의 재전송을 깨끗하게 다시 받을 수 있다.
5. **처리 결과를 이벤트 행에 남긴다.** `APPLIED`, `ALREADY_APPLIED`, `DUPLICATE_EVENT`, `UNKNOWN_PAYMENT`, `AMOUNT_MISMATCH`, `CONFLICT_STATE`, `UNHANDLED` 중 하나다. 금액이 다르거나 닫힌 결제에 승인이 오면 반영하지 않고 운영자가 볼 수 있게 남긴다. 이런 경우도 200으로 답해 보낸 쪽이 무한 재전송하지 않게 한다.
6. 웹훅 경로(`/webhooks/*`)는 `@Public()`이다. web 서버용 내부 비밀값 대신 서명이 인증이다.

## 버린 대안

- **이벤트 id만으로 중복 제거**: 같은 결제에 다른 이벤트 id가 오는 경우를 막지 못한다.
- **원장 멱등키만으로 중복 제거**: 원장에 닿지 않는 이벤트(실패, 금액 불일치)의 중복·이력을 남기지 못한다.
- **"이미 승인이면 무시"를 애플리케이션 조건문으로만**: 두 웹훅이 동시에 오면 둘 다 "아직 승인 전"을 읽을 수 있다. 행 잠금과 유니크 제약이 이 경합을 DB에서 끊는다.
- **파싱한 JSON으로 서명 계산**: 키 순서·공백이 바뀌면 정상 요청도 서명이 틀린다.

## 결과

- 웹훅이 두 번 와도, 안 와도, 순서가 바뀌어도 잔액은 한 번만 바뀐다.
- 모든 수신 이벤트가 결과와 함께 남아 "그때 무엇이 왔고 어떻게 처리됐나"를 되짚을 수 있다.
- 대가: 이벤트 테이블이 계속 자란다. 보관 기간 정책은 아직 없다.

## 이 결정을 지키는 테스트

- `apps/api/test/payments.e2e-spec.ts`: 정상 승인(원장 1행). 웹훅 두 번 시나리오 `03`(이벤트 1행, 원장 1행). 잘못된 서명 401(변화 없음). 다른 이벤트 id로 승인 재수신(이벤트는 저장, 원장은 1행 유지). 금액 불일치 미반영.
- `apps/api/test/reminders.e2e-spec.ts`: 결과 웹훅 재전송 시 환불이 늘지 않는다. 배달 완료 건에 늦게 온 실패는 기록만 하고 환불하지 않는다. 위조 서명은 거절한다.
