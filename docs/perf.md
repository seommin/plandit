# 성능 측정 — 리마인더 대량 발송 (PLANDIT-30)

> **문자 1,000통을 한 번에 보내면 40%가 실패하던 것을, 중계사 속도에 맞춰 보내도록 바꿔 0%로.**
> 중계사 호출은 4,924번 → 1,008번. 병목은 DB도 워커 수도 아니라 "중계사 한도를 모르고 보내던 것"이었습니다.

## 무엇을 쟀나

- **상황**: 일정 하나에 참석자 1,000명(그리고 3,000명), 문자 리마인더 하나. 알림 시각에 1,000통이 한꺼번에 나가야 합니다.
- **중계사(모의)**: 초당 20건까지 받고 넘으면 `429`. 결과는 3초 뒤 웹훅. 무작위 실패 0%, 끝자리 9("없는 번호") 제외 → **실패는 전부 우리 쪽**입니다.
- **측정**: 알림 시각부터
  - 묶어 만들기: 발송 건 1,000행 기록 + 발송 작업 등록이 끝날 때까지
  - 발송 지연: 각 문자가 중계사에 접수된 시각
  - 끝: 마지막 결과(성공·실패)가 기록된 시각
  - 중계사 호출: 429로 되돌아와 다시 보낸 것까지 센 횟수(워커 지표 `plandit_jobs_total`)
  - 돈: `차감 = 성공 + 환불`이 맞는지
- **환경**: Windows 11 노트북, Docker의 PostgreSQL 18·Redis 7, Node 24, 워커 1개(동시성 10), 재시도 최대 6번(1·2·4·8·16초 + 지터)

## 결과

| | 개선 전 1,000명 | 개선 전, 동시성 50 | 개선 전 3,000명 | **개선 후 1,000명** | **개선 후 3,000명** |
| --- | ---: | ---: | ---: | ---: | ---: |
| 성공 | 602 | 576 | 958 | **1,000** | **3,000** |
| 실패(재시도 소진, 환불) | 398 (40%) | 424 (42%) | 2,042 (68%) | **0** | **0** |
| 중계사 호출 | 4,924 | 4,948 | 15,641 | **1,008** | **3,007** |
| 발송 속도(통/초, 한도 20) | 17.3 | 16.4 | 19.9 | 19.3 | 19.6 |
| 묶어 만들기 | 0.2초 | 0.3초 | 0.5초 | 0.4초 | 0.5초 |
| 발송 지연 p50 / p95 | 16 / 33초 | 17 / 33초 | 24 / 47초 | 26 / 48초 | 77 / 144초 |
| 끝 | 38초 | 39초 | 52초 | 56초 | 157초 |
| 돈(`차감 = 성공 + 환불`) | 맞음 | 맞음 | 맞음 | 맞음 | 맞음 |

개선 전이 "더 빨리 끝나는" 것처럼 보이는 건, 40~68%가 재시도를 다 쓰고 **실패로 일찍 끝났기** 때문입니다.
개선 후의 끝 시각은 `보낼 수 ÷ 초당 한도`(1,000 ÷ 20 = 50초, 3,000 ÷ 20 = 150초)에 결과 대기 3초를 더한 값과 거의 같습니다. 중계사 한도가 정하는 최솟값입니다.

## 원인

PLAN에서는 병목을 "배치 INSERT, 워커 동시성"으로 예상했지만 둘 다 아니었습니다.

- **묶어 만들기는 이미 한 번에** 하고 있었습니다(`createMany` 1번 + `addBulk` 1번). 3,000건도 0.5초입니다.
- **워커가 중계사 한도를 모른 채** 동시성(10)만큼 보내고, 429는 지수 백오프 재시도로만 받았습니다.
  1. 1초에 20건만 통과하고 나머지는 429를 받고 1·2·4·8·16초 뒤에 다시 몰려옵니다.
  2. 재시도 6번(약 31초)이 끝날 때까지 차례가 오지 않은 문자는 `RELAY_UNAVAILABLE`로 실패하고 환불됩니다.
  3. 보낼 문자가 `31초 × 20건` ≈ 600건을 넘으면 실패가 반드시 생깁니다.
- **동시성을 올려도 소용없습니다**(50: 실패 42%). 더 많이 쏠 뿐이고 통과량은 중계사가 정합니다.

돈은 모든 경우에 맞았습니다(차감한 건은 성공하거나 정확히 한 번 환불). 고객 입장에서는 "**알림이 안 왔다**"가 문제였습니다.

## 고친 것

- 유료 발송(문자·알림톡)을 별도 큐 `reminder-sends`로 옮겼습니다. 이 큐는 BullMQ limiter로 **초당 `RELAY_SEND_RPS`건만**(기본 20 = 중계사 계약 한도) 꺼냅니다.
- 한도 수는 Redis에 있어서 **워커를 여러 대 띄워도 합계로** 지켜집니다.
- 차례를 기다리는 동안에는 작업이 시작되지 않으니 재시도 횟수도 쓰지 않습니다. 재시도는 진짜 장애(5xx·연결 실패)를 위해 남습니다.
- 푸시는 중계사를 거치지 않으므로 한도 없는 기존 큐(`reminders`)에 그대로 둡니다. 대량 문자 때문에 푸시가 늦어지지 않습니다.
- 남은 429(1,000통에 8번)는 우리 1초 창과 중계사 1초 창이 어긋나는 경계에서 생기고, 기존 백오프로 처리됩니다.

e2e(`reminders.e2e-spec.ts`)가 "101통 발송에서 429 재시도 5건 이하"를 지킵니다. 한도 없이 돌리면 72건이 나와 이 테스트가 실패합니다.

## 다시 재기

```bash
pnpm perf:reminders
```

- 별도 DB(`<DB 이름>_perf`), Redis 3번, 포트 4101(모의 중계사)·4002(api)·4193(워커 지표)에서 서버를 띄우고, 측정한 뒤 끕니다.
- `pnpm dev`나 개발 데이터와 섞이지 않습니다. 측정 스크립트는 이름이 `_perf`로 끝나는 DB에서만 돕니다.
- `KEY=값` 인자로 설정을 바꿉니다.
  - 개선 전 동작: `pnpm perf:reminders RELAY_SEND_RPS=1000000`(사실상 한도 없음)
  - 동시성: `REMINDER_SEND_CONCURRENCY=50`
  - 규모: `PERF_RECIPIENTS=3000`(최대 9,000)

## 남은 한계

- **큰 발송은 마지막 사람이 늦게 받습니다.** 3,000통이면 약 2.5분이고, 중계사 한도 안에서는 피할 수 없습니다. 필요해지면 큰 발송을 알림 시각보다 먼저 시작하거나 중계사 한도를 올리는 계약이 답입니다.
- **한 워크스페이스의 대량 발송이 다른 워크스페이스의 문자를 기다리게 합니다**(큐가 하나). 워크스페이스별 공정 분배는 BullMQ 그룹 같은 기능이 필요하고, 지금 규모에서는 하지 않았습니다.
